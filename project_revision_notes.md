# Project Revision Notes

These notes summarize the recommended file-writing order for this data engineering project and the API concepts discussed.

## Project Big Picture

This project is a weather data engineering pipeline.

```text
Open-Meteo API
    -> extract weather data
    -> save raw CSV
    -> upload raw CSV to Azure
    -> transform and clean data
    -> validate processed data
    -> upload processed CSV to Azure
    -> load data into PostgreSQL
    -> expose data through FastAPI
    -> visualize in Power BI
```

The most important flow is:

```text
extract -> transform -> validate -> load -> serve API
```

## Recommended Coding Order From Zero

If the project starts with no files, write the useful files in this order.

1. `requirements.txt`

   List all Python libraries needed by the project.

   Example libraries:

   ```text
   requests
   pandas
   azure-storage-blob
   python-dotenv
   schedule
   psycopg2-binary
   sqlalchemy
   fastapi
   uvicorn[standard]
   ```

2. `.env`

   Store secret and environment values.

   Example:

   ```text
   AZURE_STORAGE_CONNECTION_STRING=...
   AZURE_CONTAINER_NAME=weather-data
   POSTGRES_HOST=localhost
   POSTGRES_PORT=5432
   POSTGRES_DB=weather_db
   POSTGRES_USER=postgres
   POSTGRES_PASSWORD=postgres
   ```

   Do not upload `.env` publicly.

3. `src/config.py`

   Central place for configuration.

   It reads values from `.env` and defines shared paths such as:

   ```text
   data/raw/weather_raw.csv
   data/processed/weather_cleaned.csv
   PostgreSQL connection URL
   Azure connection values
   ```

4. `src/logger.py`

   Sets up logging for the pipeline.

   This helps you know whether the pipeline succeeded or failed.

5. `src/extract.py`

   Calls the Open-Meteo API and saves raw weather data.

   Main job:

   ```text
   call external API -> receive JSON -> convert to DataFrame -> save raw CSV
   ```

6. `src/transform.py`

   Reads the raw CSV, cleans the data, adds useful columns, and saves processed data.

   Example new columns:

   ```text
   temperature_category
   rain_status
   ```

7. `src/validate.py`

   Checks that the processed data is correct before loading.

   Example checks:

   ```text
   required columns exist
   DataFrame is not empty
   no null values in important columns
   latitude and longitude are valid
   humidity is between 0 and 100
   datetime columns are valid
   rain_status contains only valid values
   ```

8. `src/upload_to_azure.py`

   Uploads local CSV files to Azure Blob Storage.

   It uploads:

   ```text
   raw CSV -> Azure raw layer
   processed CSV -> Azure processed layer
   ```

9. `src/load.py`

   Loads processed data into PostgreSQL.

   Main job:

   ```text
   read processed CSV -> create table if needed -> append rows to PostgreSQL
   ```

10. `main.py`

    Combines all ETL steps into one pipeline.

    Main flow:

    ```text
    setup logger
    extract data
    upload raw data
    transform data
    validate data
    upload processed data
    load data into PostgreSQL
    ```

11. `api.py`

    Creates your own API using FastAPI.

    Write this only after database loading works.

    Example API endpoints:

    ```text
    /
    /weather/latest
    /weather/city/{city}
    /weather/summary
    ```

12. `Dockerfile`

    Write this after `main.py` works locally.

    It lets the project run inside a Docker container.

13. `docker-compose.yml`

    Only needed if you want to run extra services such as Airflow using Docker Compose.

14. `airflow/dags/weather_pipeline_dag.py`

    Only needed if you want scheduled pipeline execution.

    Example:

    ```text
    run the pipeline every hour
    ```

15. `powerbi/weather_dashboard_measures.dax`

    Only needed after PostgreSQL has data.

    Contains dashboard measures for Power BI.

16. `powerbi/dashboard_build_guide.md`

    Documentation for building the Power BI dashboard.

17. `README.md`

    Write this last, after the real system works.

    The README should describe what the project does, how to run it, and what the architecture looks like.

## API Concepts

### What Is An API?

An API is a controlled way for one system to talk to another system.

In this project, there are two API ideas:

```text
1. Your code calls Open-Meteo API to get weather data.
2. Your project creates its own API so other users/apps can get your processed data.
```

## `extract.py` API Call

In `src/extract.py`, this code calls someone else's API:

```python
response = requests.get(url, timeout=10)
response.raise_for_status()
data = response.json()
```

This means:

```text
your Python code -> calls Open-Meteo API -> receives JSON weather data
```

So `extract.py` is a client or requester.

Flow:

```text
extract.py
    -> requests.get()
    -> Open-Meteo API
    -> JSON response
    -> save raw CSV
```

Simple meaning:

```text
requests.get() = your code calls another API
```

## Your Own API With FastAPI

In `api.py`, your project creates its own API.

Example:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/weather/latest")
def get_latest_weather():
    return {"data": []}
```

This means:

```text
when someone visits /weather/latest,
run get_latest_weather(),
then return JSON data
```

So `api.py` is a server/provider.

Flow:

```text
user/browser/frontend/Power BI
    -> calls your API
    -> FastAPI route runs
    -> query PostgreSQL
    -> return JSON data
```

Simple difference:

```text
extract.py with requests = you call someone else's API
FastAPI in api.py = you create your own API for others to call
```

## FastAPI Vs Uvicorn

FastAPI and Uvicorn work together, but they do different jobs.

```text
FastAPI = builds/defines the API routes
Uvicorn = runs/serves the API on a real web server
```

FastAPI defines routes such as:

```text
/weather/latest
/weather/city/{city}
/weather/summary
```

Uvicorn makes those routes reachable in a browser or by another app.

Run locally:

```bash
uvicorn api:app --reload
```

Meaning:

```text
uvicorn = start the server
api = use api.py
app = use the FastAPI object named app
--reload = restart automatically when code changes
```

Local API URL:

```text
http://127.0.0.1:8000
```

Interactive API documentation:

```text
http://127.0.0.1:8000/docs
```

## What Does `uvicorn[standard]` Mean?

In `requirements.txt`:

```text
uvicorn[standard]
```

means:

```text
install uvicorn plus recommended optional dependencies
```

Square brackets mean extras in Python packaging.

So:

```text
uvicorn
```

installs the basic server.

But:

```text
uvicorn[standard]
```

installs Uvicorn with extra packages for better local development and performance.

```text

```

## Deploying The API Online

To make your API available online, you need:

```text
FastAPI code
hosted server
hosted PostgreSQL database
environment variables
public URL
```

Local run command:

```bash
uvicorn api:app --reload
```

Online/container run command:

```bash
uvicorn api:app --host 0.0.0.0 --port 8000
```

`0.0.0.0` means the server can accept outside requests.

For API deployment, Dockerfile command should run the API:

```dockerfile
CMD ["uvicorn", "api:app", "--host", "0.0.0.0", "--port", "8000"]
```

For ETL pipeline execution, Dockerfile command runs the pipeline:

```dockerfile
CMD ["python", "main.py"]
```

So there are two possible container purposes:

```text
pipeline container -> runs main.py
API container -> runs uvicorn api:app
```

## Industry Importance Of API Systems

APIs are important because they make data available in a controlled and reusable way.

Without an API:

```text
users/apps may need direct database access
```

That is usually risky.

With an API:

```text
users/apps -> your API -> database
```

Benefits:

```text
easier data access
better security
one data service can support many apps
database structure can change without breaking users
automation is easier
frontend apps can show backend data safely
Power BI or other tools can consume clean data
```

Common industry pattern:

```text
ETL pipeline -> database -> API -> applications/dashboard/users
```

## Is API Mostly For Frontend?

Frontend example:

But APIs are also used by:


Better meaning:

```text
API = controlled doorway to your data or system
```

## `os.getenv()` Vs `_env()` In `config.py`

Both `os.getenv()` and `_env()` are used to read environment variables.

Simple version:

```python
import os

POSTGRES_HOST = os.getenv("POSTGRES_HOST", "localhost")
```

This means:

```text
use POSTGRES_HOST from .env
if POSTGRES_HOST is missing, use "localhost"
```

This is valid and beginner-friendly.

But `os.getenv()` only uses the default when the variable is missing completely.

If `.env` contains an empty value:

```env
POSTGRES_HOST=
```

then:

```python
os.getenv("POSTGRES_HOST", "localhost")
```

returns:

```python
""
```

It does not return `"localhost"`.

If `.env` contains:

```env
POSTGRES_HOST=None
```

then `os.getenv()` returns:

```python
"None"
```

That is text, not real Python `None`.

### Why This Project Uses `_env()`

The project has a helper like this:

```python
@staticmethod
def _env(name, default=None):
    v = os.getenv(name)

    if v is None:
        return default

    s = str(v).strip()

    if s == "" or s.lower() == "none":
        return default

    return s
```

This helper treats these values as missing:

```env
POSTGRES_HOST=
POSTGRES_HOST=None
POSTGRES_HOST=   None
```

It also removes extra spaces.

So this:

```python
POSTGRES_HOST = _env("POSTGRES_HOST") or "localhost"
```

means:

```text
use POSTGRES_HOST from .env
if missing, empty, "None", or only spaces, use "localhost"
```

### Are These Two Lines The Same?

```python
POSTGRES_HOST = _env("POSTGRES_HOST") or "localhost"
POSTGRES_HOST = os.getenv("POSTGRES_HOST", "localhost")
```

They are almost the same, but not exactly.

They are the same for normal values:

```env
POSTGRES_HOST=127.0.0.1
```

Both return:

```python
"127.0.0.1"
```

They are different for empty values, `"None"` text, and extra spaces.

| `.env` value | `os.getenv("POSTGRES_HOST", "localhost")` | `_env("POSTGRES_HOST") or "localhost"` |
| --- | --- | --- |
| `POSTGRES_HOST=127.0.0.1` | `"127.0.0.1"` | `"127.0.0.1"` |
| missing | `"localhost"` | `"localhost"` |
| `POSTGRES_HOST=` | `""` | `"localhost"` |
| `POSTGRES_HOST=None` | `"None"` | `"localhost"` |
| `POSTGRES_HOST=   localhost   ` | `"   localhost   "` | `"localhost"` |

Short memory version:

```text
os.getenv() = okay for simple config
_env() = safer because it handles missing, empty, "None", and extra spaces
```

For learning, this is fine:

```python
POSTGRES_HOST = os.getenv("POSTGRES_HOST", "localhost")
```

For a more careful project, this is safer:

```python
POSTGRES_HOST = _env("POSTGRES_HOST") or "localhost"
```
